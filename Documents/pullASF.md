# pullASF

Fetches Sentinel-1 granules into the archive — download, then reduce — one
download at a time across all hosts. Built for queue lines of the form

```
pullASF <url1> <url2> --archiveDir <A> && runS1interferogram <f1> <f2> --project <p>
```

so a failed fetch short-circuits the interferogram. The heavy lifting is the
existing `autoupdateS1.downloadOne` and `reduceSentinel1.remove_files_from_zip`;
what `pullASF` adds is idempotency, the download slot, and an exit-code contract.

Generated by [`findS1InsarPairs --onlinePairs --queue`](../../Sentinel1Phase/findS1InsarPairs.py),
which finds granules ASF holds that would complete an interferometric pair.

---

## Usage

```
pullASF URL [URL ...] --archiveDir DIR
```

```
# one pair, one acquisition of the download slot
pullASF https://.../S1A_..._E99B.zip https://.../S1A_..._BED0.zip \
        --archiveDir /Volumes/insar4/ian/Data/S1-Greenland

# what would happen, touching nothing
pullASF <url> --archiveDir <A> --check
```

---

## Options

| Option | Default | Description |
|--------|---------|-------------|
| `URL ...` | — | One or more granule URLs, fetched as **one unit of work** under a single acquisition of the download slot. |
| `--archiveDir DIR` | from `--config` | Archive root holding the `YYYY-MM` subdirs. |
| `--config FILE` | `<archiveDir>/autoupdate.yaml` | Where `archiveDir` / `reducePattern` / `tracksToExclude` come from if not given. |
| `--reducePattern PAT` | config, else `hv` | Entries matching this substring are stripped from the zip. |
| `--noReduce` | off | Download only, leaving the zip full size. |
| `--maxAttempts N` | 3 | Download attempts per granule, forwarded to `downloadOne`. |
| `--waitMinutes N` | 120 | How long to wait for the download slot — see below, this covers the whole queue ahead of you, not one download. |
| `--allowDuplicate` | off | Fetch even when another product id of the same acquisition is held. |
| `--allowExcludedTrack` | off | Fetch even if the track is in `tracksToExclude`. |
| `--check` | off | Report what would happen; change nothing. |

## What it does

1. **Fast path, no lock.** If every requested granule is already in its own
   `YYYY-MM` dir and passes `zipComplete`, print the paths and exit 0. Granules
   are reused across pairs at ~1.75x, so this is the common case and it has to
   be cheap.
2. Reject anything that is not a parseable S1 granule URL (65), a track in
   `tracksToExclude` (70), or an acquisition already held under a different
   product id (66).
3. **Take the download slot**, waiting up to `--waitMinutes`.
4. Inside the slot, for each granule still missing: `downloadOne`, then
   `remove_files_from_zip`.
5. Print the paths, exit 0.

Filing into the assembly tree is deliberately **not** done — the phase workflow
reads the zip directly, one frame at a time. A later `autoupdateS1` sweep files
these zips in its own time, renaming `.zip` → `.zip.1`.

---

## Why one call per pair

With a single download slot, chaining `pullASF a && pullASF b` interleaves at
the *granule* level: a job can win the slot for its first image early and its
second last, so nothing starts running until nearly every download has
finished. Taking the slot once per pair means each job leaves with something
runnable and its compute overlaps the next job's fetch.

For 10 jobs × 2 granules at ~170 s each, time to the first running interferogram
is ~6 min rather than ~57; job *k* starts after 2*k* downloads. Total download
time is unchanged.

---

## The download slot

One lock file, `<archiveDir>/.pullASF.download.lock`, via the existing
`autoupdateS1._tryLock`. Only one process anywhere is in the download path at a
time, which caps load on ASF and makes check-then-download atomic — two
processes cannot race the same granule because only one can be downloading at
all.

The wait loop polls **two** conditions and takes whichever comes first:

- the slot falls free, or
- everything requested has appeared, because another job fetched it — in which
  case this one returns without ever taking the slot.

That second exit is what keeps the waiter pool shrinking instead of every
waiter re-contending on each release, and it is what makes an overlapping chain
cheap: `pullASF A B` and `pullASF B C` running together means the second call
finds B already there (re-checked *inside* the slot) and pays only for C.

**Cross-machine.** Acquisition is a single `os.open(O_CREAT|O_EXCL)`, which the
NFS server resolves atomically — the archive is NFSv4.2, where exclusive create
is part of the protocol. Of N machines racing, exactly one wins and the rest get
`EEXIST` **from the server**; no client-side cache participates, so five
contenders behave exactly like two. Jittered polling stops waiters waking in
lockstep.

Timeouts are set from the ~108 s/granule the archive's `autoupdate.yaml`
records: `--waitMinutes 120` covers a full queue ahead of you, while the lock's
own stale window is 45 min, comfortably above a real ~3–10 min hold. Note these
move in opposite directions — serialising makes the *wait* longer while a single
*hold* stays short.

## Exit codes

Chosen in the sysexits range so they cannot be confused with
`runS1interferogram`'s (1, or 128+n for a signal) in `exitStatus.log`.

| Code | Meaning | `&&` chain |
|---|---|---|
| 0 | present, complete and reduced (fetched now or already there) | continues |
| 64 | no usable `archiveDir` | stops |
| 65 | URL is not a parseable S1 granule | stops |
| 66 | duplicate product id already held for this acquisition | stops |
| 67 | download slot busy and the wait expired | stops |
| 68 | download failed after `--maxAttempts` | stops |
| 69 | reduce left the zip unsound (zip removed) | stops |
| 70 | track is in `tracksToExclude` | stops |

## Things worth knowing

- **`--xferDir` is not optional polish.** `ariaDownload`'s default scan list
  starts with `'.'`, and `downloadOne` runs it with `cwd=monthDir`, so an
  existing `<name>.zip.1` there would be `shutil.move`d to `.zip` — un-filing an
  already-processed granule. `pullASF` passes `--xferDir <archiveDir>`, which
  *replaces* that list rather than appending. `--noRename` is **not** the
  alternative: it takes the same branch, skips both the move and the download,
  and leaves no file at all.
- A `.zip.1` hit ends at the fast path unconditionally, for the same reason.
- **`reduces1` is a no-op on `1SDV` (VV/VH)** scenes: the match is a plain
  substring and `'hv' not in '-vh-'`. Correct for Greenland's `1SDH`; a VV/VH
  archive would silently store full-size zips.
- **The nightly `autoupdateS1` is not coordinated with.** It can in principle
  delete and re-fetch a zip `pullASF` just created. The two separate naturally
  in time — the nightly moves forward as data arrives, this back-processes — so
  avoid aiming both at the same window.
- A reduce that fails but leaves the zip *sound* is a warning, not an error: the
  zip is usable, just larger. Only an unsound zip is removed and reported (69).
